# 外部回调模板：从模拟到签名接收

## 这次能做什么

后台顶部“外部回调”提供模板新建、查看、修改、复制、删除 / 归档、启停和版本发布。支持最多 12 步的后端 JS / 管理员浏览器计算 / 用户页面刷新排序组合。每站可以单独绑定一个已发布模板，启用签名回调接收和自动后端执行。任务事件、代码版本和结果持久保存；后台任务列表不轮询；用户页面仅在显式绑定后长轮询。

**回调能力范围。**回调模板支持本文说明的 VMQ HMAC-SHA256 通知格式，负责后续数据处理。订单金额核验、主动查单和第三方充值需要各自的业务接入。HMAC 只证明通知来自持有密钥的一方。任务的 `payment_verified` 固定为 false，流程状态和付款状态分别查看。

## 从后台生成自己的 VMQ 收款二维码

1. 先在自己管理的 VMQ 配好收款码，并为站点配置下文的签名回调。
2. 在 iframe-host 服务环境里配置 `IH_VMQ_CHECKOUT_ORIGIN`（顾客能打开的 VMQ HTTPS 域名）与 `IH_VMQ_CALLBACK_ORIGIN`（VMQ 能访问的 iframe-host HTTPS 域名）。如果服务端使用不同的 VMQ 地址，可另设 `IH_VMQ_API_ORIGIN`。这些值只填写协议和域名，可带端口。开发机的 VMQ 地址支持本机回环 HTTP。
3. 登录 iframe-host 后台，打开「外部回调 → VMQ 收银台」。选择回调站点，输入唯一业务订单号和金额，选择微信或支付宝，点击「生成收款二维码」。
4. 打开 `checkoutUrl` 可预览顾客看到的收银台。需要在自己的程序用二维码时，复制结果中的 `qrCodeContent` 或 `qrImageUrl`。应付金额展示 `amountDue`，VMQ 可能为匹配订单而稍微调整它。
5. 顾客按收银台展示的金额付款。支付确认后，VMQ 会请求所选站点的签名回调，模板可以通过 `input.payId` 关联业务订单号。收银台查询到付款后按 VMQ 配置的返回地址跳转，回调处理进度在后台查看。

登录后台的会话仅用于授权下单入口，通信密钥由服务端读取。下单响应超时或无法确认时，先按业务订单号在 VMQ 查单。生成二维码代表订单正在等待付款；VMQ 的收银台会自行查询付款状态。

## VMQ 直接接入已有 JS 模板

不另建本站收款后台，VMQ 通知直接进入已发布模板。现有任务记录用于防重复、恢复和排错，不是新增充值余额系统。

1. 登录本站后台 → 外部回调 → 新建模板，填写后端 JS → 保存并发布。
2. 编辑要接收通知的站点，选择此模板，打开“接收签名回调”和“VMQ 回调适配”。要收到后自动运行，再打开“自动执行后端步骤”。不开自动执行则只接收，需在任务详情点击执行。
3. “VMQ 通信密钥的环境变量名”填写 `IH_CALLBACK_VMQ_KEY`，也可每站使用不同的 `IH_CALLBACK_` 前缀变量。
4. 运维在 Linux 服务受保护的 EnvironmentFile 中设置该变量的值，与 VMQ 后台通信密钥一致，至少 32 字节。界面不填写密钥本身；不要把 `.env.local` 整个上传。已公开过的测试密钥应更换。
5. 保存站点后点“检查已保存回调配置”，确认 VMQ 开关、VMQ 密钥和已发布模板均正常。
6. 在 VMQ 系统设置的“回调地址”填 `https://hacket.top/__ih/callback/vmq/实际站点ID`。站点 ID 不是显示名称，也不一定是代理前缀 `666`；检查按钮会显示正确路径。订单自带回调地址时会覆盖 VMQ 系统默认地址，旧订单需要核对。
7. VMQ 回调模式建议异步。本站只有在验签并持久保存任务后才返回纯文本 `success`；它表示通知已接收，不表示脚本完成或 8888ok 账户已充值。JS 失败在任务详情中查看，不通过反复补发通知来重复充值。

通信过程：手机 → VMQ → 本站专用回调 → 已发布 JS 模板。公网 VMQ 到本站使用 HTTPS，不需要把本机 VMQ 管理后台暴露出去。

示例模板仅整理参数，不付款、不联网、不自动加余额：

```js
if (input.provider !== 'vmq') throw new Error('不是 VMQ 通知');
return {
  order_ref: input.payId,
  amount: input.reallyPrice,
  requested_amount: input.price,
  channel: input.type === '2' ? 'alipay' : 'wechat',
  business_data: input.param,
  next_action: '等待配置允许使用的原站充值执行方式'
};
```

脚本可读取 `input.payId`（业务订单号）、`input.param`（业务自定义字符串）、`input.type`（1 微信，2 支付宝）、`input.price`（订单金额字符串）、`input.reallyPrice`（实付金额字符串）、`input.eventId`、`input.timestamp`。后续步骤用上一输出作为 input；原始通知在 event。不会把 VMQ 通信密钥、签名和 nonce 暴露给脚本或任务详情。

**业务账户从哪里来？**必须在创建订单时将业务订单与账户建立关联，或把必要的账户标识放入经过本站下单流程核对的 `param`。仅从手机收到“1 元到账”无法得知应给哪个 8888ok 账户充值。不要让脚本盲信任一个用户自行提交的账户／金额。

**现在 JS 能直接给原站充值吗？**还不能。现有后端 JS 是没有网络的隔离计算，管理员浏览器 Worker 也不能访问原站 DOM；仅有用户页面定向刷新动作。接通回调不等于放开任意网络和用户凭据。下一阶段需确认原站允许的充值接口或受控浏览器流程，再增加范围受限、凭据留在服务端、可停止且防重复的执行能力；不要使用 `return {success:true}` 冒充真实充值。

技术约束：只接受当前 VMQ 的 GET + HMAC_SHA256 签名，拒绝 MD5、重复／未知参数、异常金额和无订单转账。通知按站点与 `vmq:eventId` 去重，重新生成 nonce 的补发不会重复建任务；同事件改金额／业务订单号会返回冲突。VMQ 的 timestamp 是支付时间，不是发送时间，因此允许历史补发；防重放依靠持久去重，不能删除历史记录后盲目重放。各站必须使用不同的 VMQ 密钥，VMQ 协议本身不签站点路径。Nginx 应对 VMQ 路径关闭查询字符串访问日志，避免记录业务数据及可重放签名。接收开关关闭时拒收；VMQ 开关关闭时也暂停未执行的 VMQ 模板任务。

## 后端优先：前端是否保留，怎么选

**保留，但不要把前端作为收款和充值的必经环节。**新建模板只添加一个后端步骤；新添加的浏览器步骤默认关闭，已有模板的开关和已发布任务不会被修改。编辑器实时显示开启的步骤数量、是否需要人工或用户页面，发布确认会再次提示这些依赖。

| 运行方式 | 适合做什么 | 谁需要在线 | 是否建议加入自动收款主流程 |
| --- | --- | --- | --- |
| 后端 JS | 整理回调参数、校验业务数据、计算下一步输入 | 服务器 | 推荐；无人值守还需开启站点的自动执行后端 |
| 管理员浏览器计算 | 管理员临时调试、人工数据处理 | 管理员打开后台并点击执行 | 不推荐；到这一步会暂停等待人工 |
| 用户页面刷新 | 业务处理后通知当前订单的页面更新展示 | 绑定订单的用户页面 | 可选；它会等待页面确认，后续步骤也被阻塞 |

普通用户不需要改浏览器设置、安装扩展或打开开发者工具。用户刷新需要开发者在下单流程里自动接好订单绑定；下文控制台例子仅用于开发调试，不是让顾客照着操作。若尚未接入绑定，保持用户页面通知和对应步骤关闭，直接使用纯后端模板即可。刷新步骤应放在业务处理之后；当前刷新不是独立的非阻塞通知，页面关闭、绑定丢失或过期时可能需要人工处理。

例如：先只启用“后端整理 VMQ 参数”，另外两个步骤不要添加或保持关闭。此时不依赖任何浏览器。以后确认原站允许的充值接口并实现受控接口执行能力后，再接到后端主流程中；最后按需添加“用户页面刷新”，用于更新展示。**当前版本没有网络请求执行能力，完成后端计算不等于已经给原站账户充值。**

管理员浏览器计算不是服务器的无头浏览器，也不掌握用户页面 DOM 或 Cookie。不应把它当成自动登录、扫码或自动充值的替代品。后端 `fetch` / `upstream.request` 目前均不存在，不要直接把这类示例粘贴进现有模板。

### 后续受控接口执行的框架边界（待实现）

后续接口执行应为独立的后端能力，不要求普通用户配置浏览器，也不直接向计算沙箱开放任意 Node 或网络权限：

- 管理员明确配置允许的 HTTPS 目标、路径和方法，默认关闭；禁止脚本任意访问内网或跟随重定向绕过限制。
- 凭据仅保存在服务端，通过引用使用；不传入模板、浏览器或日志。
- 执行前持久记录业务订单和防重键；超时或断连而无法确定原站是否执行时转待核对，禁止自动重复充值。
- 模拟任务默认不发真实业务请求；真实执行需另行开启，保留版本快照和脱敏结果。
- 原站接口返回和原站订单核验决定业务结果，不能根据浏览器报告、页面刷新或脚本返回的 success 判定充值成功。

以上是接入约束，不是已经可调用的 API；必须先确认原站提供的授权接口及所需权限。

## 第一次使用：不需要付款或密钥

1. 登录后台，打开“外部回调”，点“新建模板”。
2. 后端步骤写 `return { amount: Number(input.amount) + 5 };`。
3. 添加管理员计算，写 `return { ...input, reviewed: true };`。
4. 再添加后端 JS，写 `return { amount: input.amount, browserUntrusted: previous[1].trusted === false };`。
5. 保存草稿，然后“保存并发布”。草稿不运行；发布后模板启用，但不会自动打开任何站点的接收开关。
6. 选择测试站点，输入 `{"event_id":"demo","amount":100}`，点“创建模拟任务（不付款）”。
7. 在任务详情点“执行 / 继续后端”，任务进入“等待管理员计算”。
8. 点“执行管理员计算步骤”，确认后运行；再点“执行 / 继续后端”。最终输出 `amount:105`，浏览器结果仍标记为不可信。

管理员 Worker 步骤由当前登录的管理员明确执行，而不是在原站任意用户的页面自动注入。管理员离线或没有点击时任务就等待。刷新特定用户页面请使用下文独立的“用户页面刷新”步骤，不复用管理员登录凭据。

## 模板与步骤

- 模板 ID 形如 `cb-...`，创建时由服务器生成。发布递增版本号，现有任务保存完整代码快照，不因后续编辑改变。
- 已绑定站点的模板必须先解除绑定才能删除；有任务历史的模板改为归档，保留追溯信息。归档模板可查看或复制，不能执行。
- 每步可以开启 / 关闭、调整顺序、名称、运行位置和 100–3000 毫秒超时。代码最多 8 KiB；每次返回 JSON 最多 16 KiB。同步后端执行中超时的代码会被打断，外层 Worker 也有终止保护。
- `input` 是当前输入（首步为回调 JSON，后续为上一有效步骤输出）；`event` 是最初的脱敏事件；`previous` 是已执行步骤的结果，元素含 `step`、`type`、`output`、`trusted`。前端结果的 trusted 为 false；后端执行可信不代表业务内容可信。
- 用 `return` 传递结果，未返回按 null 处理。后端不支持 Promise；前端支持 Promise / await。不要只修改 input 而不返回。
- 后端由独立 Node Worker 托管 QuickJS/WASM，解释器内存上限 16 MiB，栈上限 256 KiB；代码没有 Node require、process、环境变量、文件或网络能力，不使用 Node vm 充当安全边界。
- 管理员计算在 sandbox iframe 内启动可终止 Worker；没有原站 DOM、后台 DOM、Cookie、API token 或网络。CSP 阻止出站连接。不能写 document.querySelector 去操作原站登录 / 付款控件。
- 不传入请求 Cookie、Authorization、回调签名或商户密钥。JSON 中名字含 password、secret、token、authorization、cookie、api_key、signature 等的键会脱敏。这不保证所有自由文本都不含敏感信息，发送方仍须主动最小化数据。

## 接收外部回调

1. 选择并发布模板，复制模板 ID。
2. 编辑目标站点，找到“外部回调绑定”，从候选模板 ID 中选择或粘贴。
3. 密钥环境变量名默认 `IH_CALLBACK_SIGNING_KEY`。多站点建议使用不同变量，例如 `IH_CALLBACK_SITE_A`。变量名必须以 `IH_CALLBACK_` 开头，表单里只填名字，不填密钥。
4. 在 Linux systemd 服务的受保护 EnvironmentFile 中配置至少 32 字节的强随机密钥，文件仅给运维 / 服务账号需要的权限，不提交到 Git，不在终端日志打印。服务需要重启才能读取新环境值；先确认没有活跃验证码或回调任务。
5. 打开“接收签名回调”，保存。点“检查已保存回调配置”查看密钥是否可用、已发布版本和存储健康。它不会保存未提交的表单或实际发送回调。
6. 自动执行默认关闭：通知会落盘成为“待执行”，管理员手动处理。开启后只自动执行连续后端步骤；遇到前端步骤仍等待管理员。

接收地址：`https://你的域名/__ih/callback/站点ID`，不是 `/666/...`，不要加站点代理前缀。仅支持 POST、未压缩 `application/json`，正文上限 64 KiB；事件持久输入上限 16 KiB，须包含唯一的字符串 `event_id`（1–128 个字母、数字、下划线、点、冒号或连字符）。

请求头：

- `X-IH-Timestamp`：当前 Unix 秒，十位十进制字符串，时钟容差 300 秒。
- `X-IH-Signature`：HMAC-SHA256 的小写十六进制值。
- 待签名字节为：UTF-8 的 `timestamp + "." + site_id + "."` 紧接**原始请求正文字节**。签名包含站点 ID，不能跨站重放。

发送方 Node 示例（密钥从发送方环境取，不打印）：

```js
const crypto = require('node:crypto');
const siteId = 'your-site-id';
const timestamp = String(Math.floor(Date.now() / 1000));
const body = JSON.stringify({ event_id: 'example-unique-event-001', amount: 100 });
const secret = process.env.IH_CALLBACK_SIGNING_KEY;
if (!secret || Buffer.byteLength(secret) < 32) throw new Error('Configure signing key first');
const signature = crypto.createHmac('sha256', secret)
  .update(timestamp + '.' + siteId + '.').update(body).digest('hex');
await fetch('https://your-domain.example/__ih/callback/' + siteId, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'X-IH-Timestamp': timestamp, 'X-IH-Signature': signature },
  body,
});
```

成功时返回 HTTP 200、模板发布版本的“接收成功时的回执正文”（默认 success），头 `X-IH-Job-Id` 是任务 ID。回执正文只能编辑纯文本，不能用脚本绕过验签或改变是否成功接收的状态码。接收落盘完成后才 ACK，不等待整个流程结束。

**对接易支付 / 官方支付宝 / 微信等原生通知，不能直接套这个签名示例。**须先由服务端适配器按真实渠道协议验签、核订单、查金额等，再转为通用桥接事件；或者后续新增原生适配。没有该适配时不要把支付平台通知地址直接改到这里，也不要假设它会携带 X-IH 签名。

## 去重、暂停、恢复与排错

- 去重键是站点 ID + event_id。相同原始正文重发不重复建任务，返回原任务 ACK；同 ID 改正文返回 409。同一个 JSON 改空格 / 键顺序也视为不同原始正文，因此重试必须复用原字节；只更新时间戳并重新签名即可。
- 发布新版本不影响已收到事件的代码和 ACK。模板停用时仍接收该站绑定模板的新有效通知，但不自动执行；关闭站点接收则返回 404，发送方应保留待投递事件。
- 失败任务不自动重试。后端或浏览器执行中重启服务，任务标记待核对；前端有一分钟一次性凭证，过期 / 已使用会拒绝提交。可“转人工核对”，不通过更换 event_id 盲目重做业务动作。
- 自动执行队列每进程最多一个任务，不长期空转轮询。重启时恢复尚未开始的 pending 自动任务；waiting_browser 不自动执行浏览器。
- 通知限流：每进程每分钟每站最多 30 次、全局 120 次。超限返回 429；错误签名也占额度，避免无上限验签消耗。需要外层 Nginx 限流防护。最多 100 个模板、200 个历史任务，存储文件最多 16 MiB；达到上限拒绝新事件，不丢弃去重凭证。
- 状态默认保存在配置目录的 `callback-state.json`，可用服务环境 `CALLBACK_STATE_FILE` 指向专用目录。使用临时文件、fsync、原子替换；存储损坏或写失败会关闭接收和执行，不把失败伪装成功。
- 当前状态文件面向**单服务实例**，不要多个进程共用同一文件。多副本需要未来迁移到带唯一约束和事务的数据库；当前没有自动清理 / 删除任务功能，避免丢失去重证据。备份必须保留权限与敏感性。
- 401：签名错误 / 过期；404：站点关闭 / 不存在；409：未发布、重复事件内容冲突或步骤状态不允许；413：正文超限；415：类型 / 压缩不支持；429：限流；503：密钥缺失、存储不可用或任务上限。
- 页面默认只手动刷新最近 100 个任务，详细结果按需读取。日志不打印脚本异常原文、Token 或密钥。框架仍会保存发送方选择的业务 JSON，应尽量只发送订单引用和最少必要字段。

## 刷新真实用户页面（不是管理员 Worker）

现在有三种步骤，含义不同：

| 步骤 | 在哪里运行 | 用途 |
| --- | --- | --- |
| 后端 JS | 服务器隔离解释器 | 整理回调参数、计算下一步输入 |
| 管理员浏览器计算（Worker） | 管理员打开后台的浏览器 | 手动计算 JSON，不接触用户页面；不需要时可以删掉 |
| 用户页面：刷新绑定会话 | 实际访问代理站点的用户浏览器 | 收到通知后执行刷新，相当于那个页面调用 `location.reload()` / `history.go(0)`；无需写 JS |

推荐流程：**后端处理 → 用户页面刷新 → 后端处理**。不要为刷新用户页面选择管理员 Worker。当前只允许固定刷新动作，不执行任意页面脚本、不广播给所有用户、不自动付款。

### 从零跑一次无付款演示

1. 编辑站点 → 外部回调绑定 → 开启“用户页面通知”，保存。该开关独立于接收签名回调；仅模拟测试可以不打开真实通知接收。
2. 打开该站点的代理页面，例如 `/666/` 下实际可用的页面，刷新一次加载通知助手。不要在管理后台控制台执行下一步。
3. 在这个用户页面的控制台执行以下代码；正式对接应由下单页面自动调用，用实际订单引用代替演示值：

```js
const page = await window.IHCallbackPage.bind('order-123');
console.log({page_ref: page.page_ref, order_ref: page.order_ref});
```

4. 模板添加“用户页面刷新”步骤，保存并发布。不需要填写 `history.go(0)` 或其他代码。
5. 创建模拟任务时，将刚才的 page_ref 填入 JSON：

```json
{"event_id":"demo-refresh-1","order_ref":"order-123","page_ref":"这里替换为刚才得到的page_ref","amount":100}
```

6. 在后台点“执行 / 继续后端”。任务到达刷新步骤时显示“等待指定用户页面接收刷新”，该用户页面在线且绑定有效就会自行收到通知并刷新。其他浏览器或其他绑定页面不会被刷新。
7. 后台不自动轮询任务。点“手动刷新”查看结果；模拟任务需要再点“执行 / 继续后端”跑完后续步骤。真实签名任务如果启用“自动执行后端步骤”，会在收到页面确认后继续后续流程。

这只是框架演示，不创建订单、不调用支付平台、不确认收款。

### 正式对接需要关联订单

可信的订单后端需要保存 **站点 + order_ref + page_ref** 的对应关系，完成支付渠道原生验签、金额核对等之后，才将这两个字段加入本框架的签名通知。不能直接相信浏览器声称“这个订单属于我”。page_ref 是不可猜测的目标引用；它不是登录 Token，也不是支付凭证。浏览器持有的私有通知凭证不能交给支付平台或放到回调 JSON。

绑定有效期 30 分钟。只向绑定时的站点和路径发出刷新命令；站点前缀、订单引用、目标引用必须匹配。关闭用户页面通知后拒绝注册、领取和确认；关闭站点、关闭真实接收绑定或停用模板也会阻止对应真实任务派发。服务重启会丢弃内存中的页面会话，已等待页面的任务转“待核对”，不会把它交给别的新页面。

页面在线时使用每次最多 20 秒的长轮询；**只有调用 bind 后才建立连接**。默认关闭、未绑定、调用 stop、过期或收到拒绝响应时不继续请求；短暂网络故障采用递增退避。每个会话只允许一个进行中的领取请求，每进程最多 200 个绑定。刷新确认先持久落盘、再刷新并停止监听，避免重复通知导致循环刷新。

```js
window.IHCallbackPage.status();
window.IHCallbackPage.stop();
```

页面正常刷新后会尝试从当前标签页 sessionStorage 恢复尚未使用的绑定；换到其他路径需要重新绑定。页面关闭或断网时任务保持等待，不换人派发，绑定过期后在状态检查中标记失败。关闭页面但保留绑定的会话只占用有上限的内存，不启动服务器后台轮询。

**页面确认仅表示浏览器确认收到刷新通知，不证明导航完成，更不证明到账。**确认响应丢失、浏览器崩溃等情况下可能不发生刷新，必须允许用户手动刷新；不能依靠该结果触发真实付款或重复充值。页面步骤的输出始终标记 `trusted: false`，不会修改 `payment_verified: false`。

代理页面的 CSP / 浏览器扩展若拦截通知脚本或同源连接，助手可能无法运行；不会为了运行助手自动放宽安全策略。请检查页面上 `typeof window.IHCallbackPage` 是否为 `object`。此版本尚未替你接入具体原站的下单流程，必须在下单代码中接好绑定与可信订单关联，不能仅打开开关就期待所有支付自动联动。

## 部署与检查

使用 lockfile 安装固定依赖 `npm ci --omit=dev`，必须一并部署 `callback-service.js`、`callback-routes.js`、`callback-script-worker.js`、`public/callback-admin.js`、`public/callback-browser.html` 和 `public/callback-page.js`。旧的仅上传 server.js 的部署方式不再适用；`deploy-current-fix.py` 已加保护，防止缺失依赖时覆盖运行中的服务。

部署命令为 `python ops/deploy/deploy-callbacks.py`：远程独立目录先安装固定依赖并运行解释器烟测，确认无活跃验证码 / 回调任务后才备份、切换和重启，失败自动回滚文件与依赖；生产配置保持原样，不自动打开回调开关。Linux 安装直接联网，不使用工作站代理。

运行 `npm run check`、`node test-multisite-integration.js`。回调单测使用本地随机测试密钥和虚拟事件，覆盖错误签名、跨站、过期、重复通知、版本快照、混合步骤、超时、重启、存储损坏、容量与 HTTP 权限，不调用支付平台、不付款、不触发付费验证码。
